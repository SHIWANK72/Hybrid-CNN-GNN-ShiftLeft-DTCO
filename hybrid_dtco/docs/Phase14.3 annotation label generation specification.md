# PHASE 14.3
## Official Dataset Annotation & Label Generation Specification (DALGS)

**Document Classification:** Industrial Dataset Annotation & Ground-Truth Generation Specification
**Target Venues:** IEEE TCAD · IEEE TVLSI · DAC · ICCAD · DATE — Artifact Evaluation Ready
**Predecessor Documents:** Phase 14.1 (Dataset Generation Pipeline) · Phase 14.2 (Benchmark & Dataset Acquisition Specification)
**Successor Documents:** Phase 14.4 (Feature Extraction Specification) · Phase 14.5 (Graph Construction Specification)

**Boundary Statement:** This document governs the interval **after** benchmark acquisition (Phase 14.2 delivers QA-complete, license-cleared RTL) and **before** feature extraction (Phase 14.4 consumes finished labels as one of its inputs). It specifies what ground-truth labels exist, how each is generated, from which tool and physical-design stage each originates, how every label is validated, versioned, stored, and made reproducible. It does not specify node/edge/spatial feature construction, graph topology, model architectures, training, or inference — those are out of scope by design.

## PART 1 — Annotation Philosophy

**Purpose:** Establish why ground-truth labels are treated as independently engineered, versioned artifacts rather than incidental byproducts of running EDA tools.

**Theory / Engineering Rationale:** In a supervised ML-for-EDA context, the label *is* the scientific claim. A congestion or timing prediction model is only as credible as the ground truth it was trained and evaluated against; if that ground truth is regenerated carelessly, or its provenance is unclear, every downstream number in the paper is unfalsifiable. This motivates treating annotation as a **first-class subsystem** with its own versioning, validation, and manifest — structurally parallel to how Phase 14.2 treated benchmark acquisition as a first-class subsystem rather than an implicit precondition of dataset generation.

**Ground-Truth Philosophy:** A label is only accepted into the dataset if it satisfies three properties: (1) **tool-derived**, not hand-annotated or heuristically approximated, wherever a suitable open EDA tool exists to compute it directly; (2) **traceable**, meaning every label value can be mapped back to the exact tool invocation, tool version, and input artifact that produced it; (3) **bounded-fidelity and honestly stated**, meaning where a label is a proxy (e.g., a global-route-stage congestion estimate standing in for a fully signed-off routing result) that fidelity gap is recorded as metadata, not silently presented as ground truth of unstated quality.

**Derived Labels:** Some labels (e.g., WNS/TNS, fanout statistics, logic depth) are not direct tool outputs but are computed by aggregating or transforming a tool's raw report. Derived labels are treated identically to direct labels in terms of versioning and validation, but their derivation formula is itself a versioned artifact (Part 5's `annotation_version` field covers derivation-logic changes, not only tool-version changes) — a change in how WNS is aggregated from per-endpoint slack is a labeling-methodology change, not a bugfix, and must bump the annotation version accordingly.

**Deterministic Annotation:** Every stage in the label-generation pipeline (Part 3) is executed with pinned tool versions, pinned random seeds (where the underlying tool has stochastic elements, e.g., placement-adjacent congestion estimation), and pinned constraint files, so that re-running annotation against the identical input artifacts is expected to reproduce identical labels within a documented numerical tolerance (Part 8).

**Immutable Labels:** Once a `(dataset_id, annotation_version)` pair is finalized and included in a manifest, its label values are never edited in place. A correction, methodology change, or tool upgrade produces a new `annotation_version`, and prior versions remain queryable — this mirrors Phase 14.2's benchmark-immutability principle (Part 5 of that document) applied one layer downstream.

**Scientific Reproducibility:** Immutability plus deterministic regeneration together mean any reported result can, in principle, be regenerated by a third party from the recorded manifest without contacting the original authors — the operational definition of reproducibility this project targets for Artifact Evaluation.

**Dataset Provenance:** Every label file's provenance chain runs: `benchmark_id` + `version_tag` (Phase 14.2) → physical-design stage artifact (Part 3) → label-generation tool invocation (Part 4) → `dataset_id` + `annotation_version` (this document) → eventual feature tensor (Phase 14.4, out of scope here but the consumer of this provenance chain).

**Relationship with Phase 14.2:** This document consumes Phase 14.2's `benchmarks/manifest.yaml` as its sole entry point for RTL identity; no annotation stage re-derives or overrides benchmark-level metadata (license, source URL, RTL version) — those fields are read-only inputs from the predecessor phase.

**Relationship with Phase 14.4:** This document's output manifest (Part 5/10) is the sole contract handed to Phase 14.4; feature extraction is expected to treat every label file referenced there as read-only and versioned, never regenerating a label itself — any disagreement between what Phase 14.4 needs and what this document provides is resolved by revising this document, not by ad hoc regeneration downstream.

**Industrial Annotation Workflow:** This mirrors how a production characterization team operates in a semiconductor company — silicon or simulation measurements are logged with full instrument/tool-version provenance, signed off through a QA gate, and never quietly edited after release; a correction is a new revision, not a silent patch.

**Artifact Evaluation Expectations:** AE reviewers reproducing a subset of the dataset will re-run the annotation pipeline against the pinned tool versions recorded here and expect labels within the stated tolerance (Part 8) — this is the load-bearing reproducibility claim of the entire dataset.

**Future Extensibility:** New label categories (e.g., IR drop, electromigration, listed as future work in Part 2) are admitted by extending the taxonomy and adding a new generation stage in Part 3/4 without altering the philosophy, versioning scheme, or manifest structure established here.

## PART 2 — Label Taxonomy

Twenty label categories are defined below. For labels marked **(future)**, the taxonomy entry is specified now (to fix the schema and avoid later breaking changes) but generation is not yet mandatory in the current phase, consistent with Phase 14.1's own future-scalability notes on IR drop and electromigration maturity.

### 2.1 Congestion

- **Definition:** The degree to which routing demand exceeds routing supply within a spatial region (GCell) of the design.
- **Engineering Meaning:** A leading indicator of routability failure; the primary target label for congestion-prediction ML models in the literature this dataset is built to support.
- **Units:** Dimensionless overflow ratio (demand/supply), or absolute overflow count per GCell edge.
- **Source Tool:** OpenROAD global router (FastRoute-based) overflow report.
- **Ground Truth Origin:** Post-global-route overflow map (Phase 14.1 Stage D equivalent, re-scoped here as an annotation-stage dependency — see Part 3).
- **Expected Range:** 0 (no overflow) to design-dependent maxima; pathologically congested regions can exceed 1.0 demand/supply ratio.
- **Storage Format:** HDF5 float32 raster, GCell-resolution grid.
- **Limitations:** Global-route-stage congestion is a leading estimate, not the final detailed-route congestion; documented as a fidelity gap (Part 1).
- **Industrial Importance:** Very high — congestion prediction is the single most common ML-for-EDA use case in prior literature and industrial early-stage design-space exploration.
- **Reviewer Expectations:** Reviewers will expect the overflow definition and grid resolution to be stated explicitly and consistently across all designs; inconsistent GCell sizing across benchmarks is a common, avoidable reviewer objection.

### 2.2 Power

- **Definition:** Per-cell and per-region power dissipation, decomposed into dynamic (switching) and static (leakage) components where the tool supports the decomposition.
- **Engineering Meaning:** Enables thermal ground truth (2.3) and is itself a direct prediction target for early power estimation.
- **Units:** Watts (region-aggregated) or milliwatts/microwatts (per-cell).
- **Source Tool:** OpenROAD/OpenSTA power report, using a default (documented) toggle-rate assumption in the absence of real testbench-derived switching activity.
- **Ground Truth Origin:** Post-placement or post-route netlist with associated parasitics estimate.
- **Expected Range:** Design- and node-dependent; typically microwatts (small ISCAS-class circuits) to hundreds of milliwatts (CVA6-class cores).
- **Storage Format:** HDF5 float32 raster (region-aggregated) plus CSV per-cell.
- **Limitations:** Vector-less power estimate (no real workload-derived activity factors) — a stated, not hidden, accuracy bound.
- **Industrial Importance:** High — power is a first-order design closure metric.
- **Reviewer Expectations:** The toggle-rate assumption must be stated as a fixed, documented default, not left implicit, or reviewers will (correctly) treat the power labels as unexplained.

### 2.3 Thermal

- **Definition:** Steady-state on-die temperature distribution resulting from the power density map.
- **Engineering Meaning:** Downstream consequence of power (2.2); relevant to reliability-aware early design feedback.
- **Units:** Degrees Celsius, typically reported as ΔT above a fixed ambient reference.
- **Source Tool:** OpenROAD power-based thermal proxy (or an external steady-state thermal solver taking the power map as input).
- **Ground Truth Origin:** Power label (2.2) plus floorplan geometry.
- **Expected Range:** ΔT typically in the single-digit-to-tens-of-degrees range for the design scale in this corpus.
- **Storage Format:** HDF5 float32 raster.
- **Limitations:** Proxy-level steady-state estimate, not a signoff thermal signoff result; no transient/dynamic thermal behavior captured.
- **Industrial Importance:** Moderate-to-high, particularly for the larger OOD-tier cores (CVA6, OpenTitan top-level).
- **Reviewer Expectations:** Accuracy-gap documentation against any available reference solver (even on a small validation subset) substantially strengthens reviewer confidence in this label.

### 2.4 Timing

- **Definition:** Static timing analysis results at the endpoint level (arrival time, required time, slack) under the design's clock constraint.
- **Engineering Meaning:** The basis for WNS/TNS (2.15/2.16) and a direct indicator of design closure risk.
- **Units:** Nanoseconds (slack, arrival/required time).
- **Source Tool:** OpenSTA, run against post-placement or post-route netlist with estimated or extracted parasitics.
- **Ground Truth Origin:** Placed/routed netlist plus SPEF-lite parasitics estimate plus the benchmark's pinned clock constraint (from Phase 14.2's `clock_frequency_target_mhz` metadata field).
- **Expected Range:** Slack values from strongly positive (well-met timing) to negative (violating designs, intentionally retained in the corpus as informative negative examples).
- **Storage Format:** CSV, one row per timing endpoint.
- **Limitations:** Estimated-parasitic STA, not signoff STA with full extraction; documented accuracy correlation range against signoff-grade STA is required wherever a validation subset permits measuring it.
- **Industrial Importance:** Very high — timing closure is the dominant design-closure metric in real ASIC flows.
- **Reviewer Expectations:** Reviewers scrutinize timing ground truth more than any other label category; the parasitic-estimation methodology must be fully documented (Part 4).

### 2.5 Area

- **Definition:** Physical silicon area occupied by the design's core region and, separately, by standard cells and macros.
- **Engineering Meaning:** A normalization basis for density-related labels (2.9, 2.10) and a direct efficiency metric.
- **Units:** Square micrometers (μm²).
- **Source Tool:** OpenROAD floorplan/placement reports.
- **Ground Truth Origin:** Floorplan DEF (die/core boundary) plus placed-cell geometry.
- **Expected Range:** From a few hundred μm² (ISCAS-class) to hundreds of thousands of μm² (CVA6/OpenTitan-class), technology-node-dependent.
- **Storage Format:** Scalar field within per-design metadata (CSV/YAML), not a raster.
- **Limitations:** Minimal — area is a direct, high-confidence tool output with negligible fidelity gap.
- **Industrial Importance:** High — die area is a primary cost driver in real design decisions.
- **Reviewer Expectations:** Straightforward; expected to be reported without caveat given its high measurement confidence.

### 2.6 Wirelength

- **Definition:** Total and per-net wire length, reported at global-placement and/or global-route stage.
- **Engineering Meaning:** A standard proxy for routing cost, congestion risk, and power (interconnect capacitance).
- **Units:** Micrometers (per-net); aggregate total in millimeters for larger designs.
- **Source Tool:** OpenROAD placement/routing wirelength reports (HPWL at placement stage; actual routed length at route stage).
- **Ground Truth Origin:** Placed or routed netlist geometry.
- **Expected Range:** Design-scale-dependent, spanning several orders of magnitude across the corpus (ISCAS to CVA6).
- **Storage Format:** CSV per-net; scalar aggregate in per-design metadata.
- **Limitations:** HPWL (placement-stage estimate) systematically underestimates actual routed wirelength; both values are stored, explicitly labeled by stage, to avoid ambiguity.
- **Industrial Importance:** High — a foundational proxy metric used throughout EDA optimization.
- **Reviewer Expectations:** Reviewers expect HPWL-vs-routed-length distinction to be explicit, not conflated under one "wirelength" label.

### 2.7 Routing Overflow

- **Definition:** The count or magnitude by which routing demand exceeds available routing tracks per GCell edge, per metal layer.
- **Engineering Meaning:** A finer-grained, per-layer decomposition of the aggregate congestion label (2.1).
- **Units:** Track-count overflow (integer) per GCell edge per layer.
- **Source Tool:** OpenROAD global router per-layer overflow report.
- **Ground Truth Origin:** Same global-route stage as 2.1, retained at per-layer resolution rather than aggregated.
- **Expected Range:** 0 to design-dependent maxima, typically concentrated on a small number of lower metal layers.
- **Storage Format:** HDF5 float32 raster stack (one channel per routing layer).
- **Limitations:** Same global-route-stage fidelity caveat as 2.1.
- **Industrial Importance:** High for layer-aware congestion models specifically; supplements the layer-agnostic aggregate label.
- **Reviewer Expectations:** Layer count and layer-naming convention must be documented per PDK (differs between Sky130, GF180, ASAP7).

### 2.8 Cell Density

- **Definition:** Fraction of a spatial region's area occupied by placed standard cells.
- **Engineering Meaning:** A direct placement-quality and congestion-precursor metric.
- **Units:** Dimensionless ratio [0, 1].
- **Source Tool:** Derived directly from placed-cell geometry (computed, not a raw tool report — see Part 4's derived-metric handling).
- **Ground Truth Origin:** Placed DEF.
- **Expected Range:** [0, target_utilization], bounded by the design's configured utilization target (Phase 14.1 floorplan-variant parameter).
- **Storage Format:** HDF5 float32 raster.
- **Limitations:** Minimal; direct geometric computation with negligible fidelity gap, though grid resolution choice affects interpretability (documented per Part 4).
- **Industrial Importance:** Moderate — primarily a supporting/derived feature for congestion and thermal correlation analysis.
- **Reviewer Expectations:** Grid resolution consistency with the congestion raster (2.1) is expected, to permit direct spatial correlation analysis.

### 2.9 Routing Density

- **Definition:** Fraction of available routing resource (tracks) consumed within a spatial region, independent of whether it constitutes overflow.
- **Engineering Meaning:** A pre-overflow indicator; distinguishes "busy but resolved" regions from "overflowing" regions.
- **Units:** Dimensionless ratio [0, 1] (or >1 where overflow occurs, at which point this label and 2.1/2.7 become closely related but not identical).
- **Source Tool:** OpenROAD global router demand report.
- **Ground Truth Origin:** Global-route stage.
- **Expected Range:** [0, 1] for non-overflowing regions.
- **Storage Format:** HDF5 float32 raster.
- **Limitations:** Same global-route fidelity caveat as congestion labels.
- **Industrial Importance:** Moderate-to-high, particularly for models predicting routability margin rather than binary overflow.
- **Reviewer Expectations:** The distinction between this label and routing overflow (2.7) must be explained clearly, since the two are easily conflated.

### 2.10 Via Density

- **Definition:** Count of vias per unit area, aggregated per spatial region.
- **Engineering Meaning:** A contributor to routing congestion and a known correlate of manufacturing/reliability risk not otherwise captured by wire-based congestion metrics alone.
- **Units:** Vias per μm² (region-normalized count).
- **Source Tool:** OpenROAD detailed-route or global-route via report (fidelity depends on whether detailed routing is run for the given sample — documented per sample).
- **Ground Truth Origin:** Route-stage geometry.
- **Expected Range:** Design- and layer-count-dependent; higher in dense, multi-layer-crossing regions.
- **Storage Format:** HDF5 float32 raster.
- **Limitations:** Highest-fidelity via-density labels require detailed routing, which is not run for every sample (cost reasons per Phase 14.1); samples lacking detailed-route data carry a global-route-stage via estimate instead, and the distinction is recorded per sample in metadata.
- **Industrial Importance:** Moderate; increasingly relevant at advanced nodes where via reliability is a first-order concern.
- **Reviewer Expectations:** The detailed-route-vs-global-route provenance distinction must be an explicit per-sample metadata field, not a corpus-wide assumption.

### 2.11 Clock Skew

- **Definition:** The difference in clock signal arrival time between two sequential elements sharing (nominally) the same clock edge.
- **Engineering Meaning:** A direct timing-closure risk factor, particularly relevant for larger, multi-region designs where clock tree balancing is non-trivial.
- **Units:** Picoseconds or nanoseconds.
- **Source Tool:** OpenROAD clock-tree-synthesis (CTS) report / OpenSTA clock analysis.
- **Ground Truth Origin:** Post-CTS netlist and clock tree geometry (Part 3 Stage: CTS).
- **Expected Range:** Sub-nanosecond for small designs; up to low-nanosecond range for larger, less-balanced trees.
- **Storage Format:** CSV, per-endpoint-pair or aggregated global/local skew statistics.
- **Limitations:** Only meaningful for samples where CTS is actually run (small combinational-only benchmarks such as ISCAS-85 lack a clock tree entirely and are marked not-applicable for this label).
- **Industrial Importance:** High for sequential, clock-tree-bearing designs.
- **Reviewer Expectations:** Not-applicable designs must be explicitly marked rather than silently omitted, to avoid the appearance of missing data.

### 2.12 Clock Latency

- **Definition:** Insertion delay from the clock source to a given sequential element.
- **Engineering Meaning:** Complements skew; relevant to setup/hold margin calculations.
- **Units:** Picoseconds or nanoseconds.
- **Source Tool:** Same OpenROAD CTS / OpenSTA source as 2.11.
- **Ground Truth Origin:** Post-CTS clock tree.
- **Expected Range:** Design-scale-dependent; larger designs with deeper clock trees exhibit higher latency.
- **Storage Format:** CSV, per-endpoint.
- **Limitations:** Same CTS-applicability caveat as 2.11.
- **Industrial Importance:** Moderate-to-high, closely tied to timing closure (2.4).
- **Reviewer Expectations:** Consistent units and reference point (clock source definition) must be documented per design.

### 2.13 Critical Path Delay

- **Definition:** The maximum arrival-time path delay across the design under the given clock constraint.
- **Engineering Meaning:** The single scalar most directly tied to achievable maximum operating frequency.
- **Units:** Nanoseconds.
- **Source Tool:** OpenSTA.
- **Ground Truth Origin:** Same STA run producing the timing label (2.4); this is a derived scalar summary of that same dataset.
- **Expected Range:** Design- and clock-constraint-dependent.
- **Storage Format:** Scalar field in per-design metadata.
- **Limitations:** Inherits the estimated-parasitic caveat from 2.4.
- **Industrial Importance:** Very high — a headline design-closure number in industrial practice.
- **Reviewer Expectations:** Must be explicitly cross-referenced to the WNS label (2.15) so the two are not mistaken for independent measurements.

### 2.14 WNS (Worst Negative Slack)

- **Definition:** The most negative (worst) slack value across all timing endpoints; zero or positive if the design meets timing.
- **Engineering Meaning:** The standard industrial scalar summary of timing closure status.
- **Units:** Nanoseconds.
- **Source Tool:** Derived from the OpenSTA per-endpoint slack report (2.4).
- **Ground Truth Origin:** Aggregation of the timing label; a **derived label** per Part 1's derived-label definition, with its aggregation formula (minimum over all endpoint slacks) versioned explicitly.
- **Expected Range:** Negative (violating) to positive (comfortably met), design- and constraint-dependent.
- **Storage Format:** Scalar field in per-design metadata.
- **Limitations:** Single-point summary; discards distributional information retained separately in the full per-endpoint timing label (2.4).
- **Industrial Importance:** Very high; the single most commonly reported timing-closure scalar in industrial sign-off.
- **Reviewer Expectations:** The aggregation definition (strict minimum, not a percentile or trimmed statistic) must be stated unambiguously.

### 2.15 TNS (Total Negative Slack)

- **Definition:** The sum of all negative slack values across all violating timing endpoints.
- **Engineering Meaning:** Captures the *breadth* of a timing violation, complementing WNS's depth-only view.
- **Units:** Nanoseconds.
- **Source Tool:** Derived from the same OpenSTA per-endpoint slack report as WNS.
- **Ground Truth Origin:** Derived-label aggregation (sum over negative-slack endpoints only), versioned identically to WNS.
- **Expected Range:** Zero (no violations) to large negative values for heavily violating designs.
- **Storage Format:** Scalar field in per-design metadata.
- **Limitations:** Sensitive to endpoint count, which varies by design scale — cross-design TNS comparison requires normalization, which is a Phase 14.4 concern and explicitly out of scope here.
- **Industrial Importance:** High, typically reported alongside WNS as a paired closure-quality indicator.
- **Reviewer Expectations:** Reviewers expect WNS and TNS to be reported together, never one without the other, per standard industrial STA reporting convention.

### 2.16 Fanout Statistics

- **Definition:** Distribution of net fanout (number of sink pins per driven net) across the design.
- **Engineering Meaning:** A structural indicator correlated with both timing risk (high fanout increases delay) and congestion risk.
- **Units:** Count (integer), reported as a per-net value and as a per-design distributional summary (mean, max, percentiles).
- **Source Tool:** Derived directly from the gate-level netlist connectivity graph (no physical-design tool required; purely structural).
- **Ground Truth Origin:** Synthesized netlist (available immediately after Phase 14.1 Stage A / this document's Part 3 Synthesis stage), independent of placement/routing.
- **Expected Range:** 1 (minimum, single sink) to tens or low hundreds for high-fanout nets (e.g., reset, clock-enable signals prior to buffering).
- **Storage Format:** CSV per-net; scalar distributional summary in per-design metadata.
- **Limitations:** Minimal; a direct structural computation with no tool-fidelity gap.
- **Industrial Importance:** Moderate; a standard structural-complexity indicator.
- **Reviewer Expectations:** Clock/reset nets should be separately flagged (per Phase 14.2 Part 8's naming-normalization metadata) since their fanout statistics are qualitatively different from data-path nets and conflating them skews the distribution misleadingly.

### 2.17 Net Length

- **Definition:** Physical length of each individual net's routed (or placement-estimated) path.
- **Engineering Meaning:** The per-net decomposition underlying the aggregate wirelength label (2.6).
- **Units:** Micrometers.
- **Source Tool:** Same OpenROAD placement/routing source as 2.6.
- **Ground Truth Origin:** Placed or routed geometry, per-net.
- **Expected Range:** Sub-micrometer (adjacent-cell nets) to full-die-spanning lengths for global signals.
- **Storage Format:** CSV per-net (may be the same file as 2.6's per-net wirelength, differing only in whether it is presented per-net or aggregated).
- **Limitations:** Same HPWL-vs-routed distinction as 2.6.
- **Industrial Importance:** High as a fine-grained input to interconnect-delay and interconnect-power estimation, both downstream of this document's scope.
- **Reviewer Expectations:** Consistent with 2.6.

### 2.18 Logic Depth

- **Definition:** The number of logic-gate stages along the longest combinational path between any register/primary-input and any register/primary-output.
- **Engineering Meaning:** A structural complexity indicator correlated with, but distinct from, the timing-based critical path delay (2.13) — logic depth is gate-count-based and technology-independent, while critical path delay is technology- and constraint-dependent.
- **Units:** Count (integer number of logic stages).
- **Source Tool:** Derived directly from the synthesized gate-level netlist's combinational-path graph.
- **Ground Truth Origin:** Synthesized netlist, independent of placement/routing (available immediately post-Synthesis stage, like fanout statistics).
- **Expected Range:** Single-digit (small combinational circuits) to several tens of stages for deep, complex data paths.
- **Storage Format:** Scalar field (maximum) plus distributional summary in per-design metadata.
- **Limitations:** Purely structural; does not account for actual gate delays, hence its explicit distinction from critical path delay above.
- **Industrial Importance:** Moderate; useful as a technology-independent complexity feature.
- **Reviewer Expectations:** The distinction from critical path delay must be stated explicitly to avoid the two being treated as interchangeable.

### 2.19 Macro Density

- **Definition:** Fraction of a spatial region's area occupied by hard macros (as distinct from standard cells, per Phase 14.1's node-feature `is-macro flag`).
- **Engineering Meaning:** A first-order driver of local congestion and placement difficulty, since macros create routing blockages.
- **Units:** Dimensionless ratio [0, 1].
- **Source Tool:** Derived directly from floorplan/placement macro geometry.
- **Ground Truth Origin:** Floorplan or placed DEF.
- **Expected Range:** 0 (macro-free designs, the majority of the small/medium-tier corpus) to substantial fractions for memory-heavy designs (larger OpenTitan/CVA6 configurations).
- **Storage Format:** HDF5 float32 raster, same grid convention as cell density (2.8) for direct spatial comparison.
- **Limitations:** Minimal; direct geometric computation.
- **Industrial Importance:** High, particularly for the macro-bearing subset of the corpus.
- **Reviewer Expectations:** Grid-convention consistency with 2.8 and 2.1 is expected, as with routing density.

### 2.20 Utilization

- **Definition:** The design-wide ratio of total placed-cell area (including macros) to total core area.
- **Engineering Meaning:** The single scalar summarizing the floorplan-variant parameter deliberately swept in Phase 14.1 (utilization ∈ {50%, 65%, 75%, 85%}) — recorded here as a verification label confirming the achieved utilization matches the configured target.
- **Units:** Dimensionless ratio [0, 1], commonly reported as a percentage.
- **Source Tool:** OpenROAD placement report.
- **Ground Truth Origin:** Placed DEF.
- **Expected Range:** Matches the configured target utilization within a small tolerance (Part 8).
- **Storage Format:** Scalar field in per-design metadata.
- **Limitations:** Minimal; direct, high-confidence measurement whose primary purpose is cross-checking the floorplan-variant configuration rather than serving as a novel prediction target.
- **Industrial Importance:** Moderate as a label; high as a QA cross-check (Part 7).
- **Reviewer Expectations:** Expected to closely match the configured target; any systematic deviation is itself a QA finding worth reporting.

### 2.21 IR Drop **(future)**

- **Definition:** Voltage drop across the power distribution network under a given current-draw scenario.
- **Engineering Meaning:** A reliability/signoff-adjacent metric closely related to power (2.2) and EM (2.22).
- **Units:** Millivolts.
- **Source Tool:** OpenROAD `psm` static IR-drop analysis (available but not yet promoted to mandatory-label status in the current phase).
- **Ground Truth Origin:** Power map plus PDN geometry.
- **Expected Range:** Design- and PDN-density-dependent.
- **Storage Format:** HDF5 float32 raster (schema reserved now to avoid a future breaking manifest change).
- **Limitations:** Static analysis only in the initial future-work scope; dynamic IR drop explicitly deferred further.
- **Industrial Importance:** High in principle; deferred here purely for pipeline-maturity/cost reasons, not scientific irrelevance.
- **Reviewer Expectations:** Explicitly marking this as reserved-but-not-yet-generated (rather than omitting it from the taxonomy entirely) preempts reviewer questions about completeness.

### 2.22 Electromigration (EM) **(future)**

- **Definition:** Current-density-driven wire/via degradation risk, expressed as a ratio to a technology-defined maximum sustainable current density.
- **Engineering Meaning:** A long-term reliability metric.
- **Units:** Dimensionless ratio (current density / J_max) or absolute current density (mA/μm²).
- **Source Tool:** OpenROAD `psm` current-density analysis.
- **Ground Truth Origin:** PDN geometry plus power map, consistent with Phase 14.1 Part 4's EM label description.
- **Expected Range:** Ratio nominally ≤1 for compliant designs; corpus intentionally retains non-compliant samples as informative negative examples once generated.
- **Storage Format:** CSV per-segment plus raster overlay (schema reserved).
- **Limitations:** Rule-of-thumb-level, not signoff-grade EM analysis.
- **Industrial Importance:** High in principle; deferred alongside IR drop for the same maturity reasons.
- **Reviewer Expectations:** Consistent with 2.21 — explicit reservation, not silent omission.

## PART 3 — Label Generation Pipeline

**Purpose:** Describe the ordered sequence of physical-design stages that must be executed to produce every label in Part 2, clarifying which labels become available at which stage and why the pipeline cannot be reordered or shortcut without losing label validity.

```
RTL (Phase 14.2 acquired, Phase 14.1-preprocessed)
   │
   ▼
Synthesis            → unlocks: Fanout Statistics (2.16), Logic Depth (2.18)
   │
   ▼
Floorplanning        → unlocks: Area (2.5), Macro Density (2.19, partial — macro placement only)
   │
   ▼
Placement (global)   → unlocks: Cell Density (2.8), Macro Density (2.19, full), Utilization (2.20),
   │                             Wirelength/HPWL (2.6, placement-stage variant)
   ▼
CTS (Clock Tree Synthesis) → unlocks: Clock Skew (2.11), Clock Latency (2.12)
   │
   ▼
Routing (global, and detailed where budget permits) → unlocks: Congestion (2.1), Routing Overflow (2.7),
   │                    Routing Density (2.9), Via Density (2.10), Wirelength (2.6, routed variant),
   │                    Net Length (2.17)
   ▼
Extraction (parasitics estimation) → unlocks inputs required for: Timing (2.4)
   │
   ▼
Label Generation (STA + power/thermal solvers) → unlocks: Timing (2.4), Critical Path Delay (2.13),
   │                    WNS (2.14), TNS (2.15), Power (2.2), Thermal (2.3)
   ▼
Validation (Part 7)
   │
   ▼
Storage (Part 6)
   │
   ▼
Dataset Packaging (aggregation into the per-sample label bundle handed to Phase 14.4)
```

**Inputs:** QA-complete, license-cleared RTL and its Phase 14.2 metadata; Phase 14.1's floorplan-variant configuration (utilization/aspect-ratio targets) as the physical-design parameterization.
**Outputs:** A complete per-sample label bundle covering every applicable Part 2 taxonomy entry, plus the per-stage intermediate artifacts (DEF snapshots, STA reports) retained for traceability.
**Dependencies:** Yosys, OpenROAD (placement, CTS, global/detailed routing, `psm` power/IR analysis), OpenSTA, the pinned PDK.
**Runtime Expectations:** Dominated by the Placement and Routing stages, consistent with the per-stage runtime figures already established in Phase 14.1 Parts C/D; end-to-end per-sample annotation runtime ranges from roughly 2–5 minutes (ISCAS/ITC-99-class, all stages) to 30–90+ minutes (CVA6/OpenTitan-class, all stages including detailed routing where run).
**Memory Expectations:** Peak memory is governed by the Placement and Routing stages, consistent with Phase 14.1's per-stage figures (4–24 GB depending on design scale).
**Failure Conditions:** Any stage failure halts label generation for that specific `(benchmark_id, floorplan_variant)` sample and marks it "annotation-incomplete" rather than producing a partially-labeled sample silently; partial-stage completion (e.g., synthesis- and placement-stage labels available but routing failed) is recorded explicitly per-label rather than treating the whole sample as failed, since structural labels (fanout, logic depth) remain valid even if routing does not converge.
**Validation:** Each stage's output is validated against Part 7's QA checks before the pipeline proceeds to the next stage — a corrupted placement, for instance, must not be allowed to silently propagate into an invalid congestion label.
**Industrial Notes:** This pipeline is deliberately identical in stage ordering to Phase 14.1's dataset-generation pipeline; Phase 14.3 does not introduce a parallel physical-design flow but rather specifies, at each of the same stages, precisely which labels are extracted and how — the two documents describe the same execution but from generation-orchestration (14.1) versus label-taxonomy (14.3) perspectives respectively.
**Reviewer Expectations:** The explicit stage-to-label mapping above directly answers a common reviewer question — "at what point in the flow was this label actually knowable?" — which matters for judging whether a model's predictive claim (early-stage input → late-stage label) is honestly framed.
**Future Scalability:** Additional label categories (IR drop, EM, once promoted from future-work status) attach to the existing Routing/Label-Generation stages without requiring new pipeline stages, since the necessary PDN and power-map inputs are already produced by stages already present in this pipeline.

## PART 4 — Ground Truth Specification

This part fixes, for each metric family, the precise definition, tool origin, units, spatial resolution, coordinate system, and stated tolerance/accuracy — the level of detail an independent party needs to regenerate or audit any single label value.

### 4.1 Congestion Ground Truth
- **Definition:** Per-GCell-edge overflow = (routing demand − routing supply) / routing supply, aggregated to a per-GCell scalar by taking the maximum edge overflow bordering that cell.
- **Tool Origin:** OpenROAD global router.
- **Units:** Dimensionless ratio.
- **Resolution:** GCell grid, with GCell size fixed per PDK (recorded in metadata, Part 5) rather than fixed in absolute micrometers, so grid resolution scales consistently with technology node.
- **Coordinate System:** Die-relative Cartesian, origin at core-area lower-left corner, consistent with the coordinate convention already established for node features in Phase 14.1 Part 5.1.
- **Tolerance:** Re-running global routing with identical seed/config is expected to reproduce overflow values within a small numerical tolerance (Part 8) attributable to solver floating-point non-associativity, not methodology drift.
- **Accuracy:** Global-route-stage estimate; not validated against detailed-route congestion in the initial release (a stated limitation, not a hidden one), with a documented accuracy-gap study recommended as a QA subset study (Part 7) wherever detailed routing is available for comparison.
- **Limitations:** See Part 2.1.

### 4.2 Timing Ground Truth
- **Definition:** Per-endpoint slack = required arrival time − actual arrival time, computed under the design's pinned clock constraint.
- **Tool Origin:** OpenSTA.
- **Units:** Nanoseconds.
- **Resolution:** Per-endpoint (register input pin or primary output), not spatially rasterized.
- **Coordinate System:** Not spatial; endpoint-indexed by instance/pin name, cross-referenced to the placed coordinate of that instance via the node-feature table (a Phase 14.4 join, not performed here).
- **Tolerance:** Estimated-parasitic STA reruns under identical extraction settings are expected to match to sub-picosecond precision (deterministic solver, no stochastic element); the larger, stated uncertainty is the *estimated-vs-signoff* parasitic gap, not run-to-run nondeterminism.
- **Accuracy:** Estimated-parasitic STA is known to diverge from signoff-grade STA using full extraction; wherever a signoff-grade reference is available for even a small validation subset, an explicit correlation coefficient must be computed and reported (Part 9), rather than assumed.
- **Limitations:** See Part 2.4.

### 4.3 Power Ground Truth
- **Definition:** Per-cell power = dynamic power (switching-activity-weighted) + static/leakage power, aggregated per spatial region for the raster label.
- **Tool Origin:** OpenROAD/OpenSTA power analysis.
- **Units:** Watts (region), microwatts (per-cell, small designs).
- **Resolution:** Per-cell for the CSV label; same GCell-equivalent raster grid as congestion for the spatial label, to enable direct cross-label correlation analysis.
- **Coordinate System:** Same die-relative convention as 4.1.
- **Tolerance:** Deterministic given a fixed toggle-rate assumption; the toggle-rate assumption itself (not solver nondeterminism) is the dominant source of any power-label uncertainty and is documented as a fixed default value applied uniformly across the corpus.
- **Accuracy:** Vector-less estimate; documented as such, with no implied claim of workload-representative accuracy.
- **Limitations:** See Part 2.2.

### 4.4 Thermal Ground Truth
- **Definition:** Steady-state ΔT above ambient, computed from the power density map via a simplified thermal solver.
- **Tool Origin:** OpenROAD-integrated or external steady-state thermal proxy.
- **Units:** Degrees Celsius (ΔT).
- **Resolution:** Same raster grid as the power label (4.3), by construction (thermal is a direct function of power density).
- **Coordinate System:** Same die-relative convention.
- **Tolerance:** Deterministic given a fixed power map and solver configuration.
- **Accuracy:** ±5–10% versus a reference solver on a documented validation subset (consistent with Phase 14.1 Part 4's original figure), explicitly not signoff-grade.
- **Limitations:** See Part 2.3.

### 4.5 Area Ground Truth
- **Definition:** Core-area bounding box (width × height) and, separately, sum of placed-cell/macro footprint areas.
- **Tool Origin:** OpenROAD floorplan/placement reports.
- **Units:** μm².
- **Resolution:** Single scalar per design, not rasterized.
- **Coordinate System:** N/A (scalar).
- **Tolerance:** Deterministic, exact (direct geometric sum, no solver approximation involved).
- **Accuracy:** Effectively exact given correct DEF parsing; treated as a high-confidence reference label useful for sanity-checking other labels (Part 7).
- **Limitations:** See Part 2.5.

### 4.6 Wirelength Ground Truth
- **Definition:** Sum of per-net HPWL (placement stage) or actual routed length (routing stage), reported separately and never conflated.
- **Tool Origin:** OpenROAD placement (HPWL) and routing (actual length) reports.
- **Units:** μm (per-net), mm (design-aggregate for larger designs).
- **Resolution:** Per-net.
- **Coordinate System:** Derived from per-pin coordinates in the same die-relative convention.
- **Tolerance:** Deterministic given fixed placement/route solution.
- **Accuracy:** HPWL is a known lower-bound estimate of actual routed length by construction (a geometric property, not a tool limitation) — this relationship is documented, not treated as an error.
- **Limitations:** See Part 2.6.

### 4.7 Cell Density Ground Truth
- **Definition:** Placed standard-cell footprint area within a GCell-equivalent raster bin, divided by bin area.
- **Tool Origin:** Derived computation over placed DEF geometry (no dedicated EDA-tool report; a project-internal deterministic computation, documented as such per Part 1's derived-label handling).
- **Units:** Dimensionless ratio [0, 1].
- **Resolution:** Same raster grid as congestion/power, for cross-label spatial alignment.
- **Coordinate System:** Same die-relative convention.
- **Tolerance:** Deterministic, exact given a fixed placement.
- **Accuracy:** Exact by construction.
- **Limitations:** See Part 2.8.

### 4.8 Routing Density Ground Truth
- **Definition:** Consumed routing track fraction per GCell edge, aggregated per GCell, prior to any overflow threshold being applied.
- **Tool Origin:** OpenROAD global router demand report.
- **Units:** Dimensionless ratio.
- **Resolution:** Same GCell grid as congestion.
- **Coordinate System:** Same die-relative convention.
- **Tolerance/Accuracy:** Same characteristics as 4.1, since both derive from the same global-route run.
- **Limitations:** See Part 2.9.

### 4.9 Clock Metrics (Skew, Latency)
- **Definition:** As specified in Part 2.11/2.12.
- **Tool Origin:** OpenROAD CTS engine plus OpenSTA clock-path analysis.
- **Units:** Picoseconds/nanoseconds.
- **Resolution:** Per sequential-element-pair (skew) or per sequential element (latency).
- **Coordinate System:** Not spatial; instance-indexed, joinable to placed coordinates downstream.
- **Tolerance:** Deterministic given fixed clock-tree solution and STA settings.
- **Accuracy:** Bound by the same estimated-parasitic caveat as general timing (4.2), since clock-path delay estimation uses the same extraction methodology.
- **Limitations:** Not-applicable for clock-free combinational-only benchmarks, explicitly recorded rather than omitted (Part 2.11).

### 4.10 Macro Metrics
- **Definition:** Macro Density (2.19) and macro-adjacent structural counts (macro instance count, aggregate macro area fraction).
- **Tool Origin:** Floorplan/placement DEF macro geometry.
- **Units:** Dimensionless ratio (density); count (instance count); μm² (aggregate area).
- **Resolution:** Same raster grid as cell density, for density; scalar for counts.
- **Coordinate System:** Same die-relative convention.
- **Tolerance/Accuracy:** Deterministic, exact given fixed placement, consistent with 4.7's reasoning.
- **Limitations:** See Part 2.19.

**Inputs (Part 4, overall):** All Part 3 stage outputs.
**Outputs:** The fully specified, tolerance-bounded label set consumed by Part 6's storage layer.
**Dependencies:** Consistent with Part 3.
**Runtime/Memory Expectations:** Not separately incurred beyond Part 3's stage costs; Part 4 defines interpretation and tolerance, not additional computation, with the exception of the derived-label computations (cell density, macro density, fanout statistics, logic depth) which are lightweight (seconds) post-processing steps over already-produced geometry/netlist data.
**Failure Conditions:** A ground-truth value falling outside its documented expected range (Part 2) without an accompanying explanation (e.g., a deliberately negative-slack sample) is treated as a QA flag (Part 7), not silently accepted.
**Validation:** Every metric in this part is subject to the QA and cross-tool consistency checks specified in Part 7.
**Industrial Notes:** Fixing tolerance and accuracy claims per metric, rather than one blanket "our labels are accurate" statement, is standard practice in any measurement-based engineering specification and is what allows this document to support quantitative reviewer claims later (Part 14).
**Reviewer Expectations:** This level of per-metric precision is the primary artifact that distinguishes a rigorous ML-for-EDA dataset paper from one that will draw an accuracy-unsubstantiated-claims objection.
**Future Extensibility:** IR drop and EM (Part 2.21/2.22) will receive an identical Part-4-style entry at the point they are promoted out of future-work status, following the same definition/tool-origin/units/resolution/coordinate-system/tolerance/accuracy structure established here.

## PART 5 — Annotation Metadata

**Purpose:** Define the complete, schema-validated metadata record accompanying every annotated sample, ensuring full reproducibility and auditability independent of the label values themselves.

| Field | Justification |
|---|---|
| `dataset_id` | Primary key linking this annotation record to the specific Phase 14.1 sample (design + floorplan variant); the anchor for all downstream Phase 14.4 joins. |
| `benchmark_id` | Direct reference to the Phase 14.2 benchmark identity; ensures annotation provenance is traceable back through acquisition, not just to a local file. |
| `version` | The benchmark `version_tag` (Phase 14.2 Part 5) actually used to generate this annotation — required because a benchmark may be re-acquired at a new version while old annotations remain valid references to the old version. |
| `annotation_version` | Independent semantic version (Part 10) tracking changes to labeling methodology/tool versions distinct from the underlying benchmark version — the two must never be conflated, since a benchmark can be unchanged while annotation methodology evolves, or vice versa. |
| `OpenROAD version` | Exact OpenROAD build/commit used; pins the dominant source of physical-design-stage labels. |
| `Yosys version` | Exact Yosys build/commit used for the synthesis-stage structural labels (fanout, logic depth). |
| `PDK` | Which open PDK (Sky130/GF180/ASAP7) was used; required since every physical label is technology-node-dependent. |
| `technology node` | Redundant-but-explicit companion to `PDK` (e.g., "130nm") for human readability and for filtering without needing a PDK-name lookup table. |
| `clock frequency` | The pinned clock constraint used for this specific annotation run; required to interpret every timing-derived label (4.2, 4.9, 2.13–2.15) correctly. |
| `constraint version` | Version identifier for the `.sdc`-equivalent constraint file (Phase 14.2 Part 8), since constraint authoring can itself be revised independent of the RTL. |
| `tool commit hash` | Aggregate field (or structured sub-map) capturing exact commit hashes for every tool in the Part 3 pipeline, beyond just OpenROAD/Yosys, for full reproducibility. |
| `runtime` | Wall-clock duration of the annotation run, recorded for performance-regression monitoring and for setting realistic expectations in the paper's methodology section. |
| `timestamp` | ISO-8601 datetime of annotation generation; required for chronological audit and for correlating with any tool-version changes over the project's history. |
| `host machine` | Identifier of the machine/cluster node that generated the annotation; supports cross-machine reproducibility validation (Part 8). |
| `CPU` | CPU model/core-count of the host; relevant because some solver behaviors (thread-count-dependent placement, e.g.) can introduce minor numerical nondeterminism. |
| `memory` | Peak memory consumed during annotation; supports capacity planning for future re-runs and cluster scheduling. |
| `random seed` | Explicit seed for any stochastic stage (placement-adjacent solvers); required for the deterministic-rerun claim in Part 8 to be meaningful. |
| `checksum` | SHA-256 (or equivalent) over the finalized label bundle; the primary integrity-verification mechanism, consistent with Phase 14.2's checksum discipline. |
| `annotation status` | Enumerated: `complete`, `partial` (some Part 3 stages failed but structural labels remain valid), `failed`. |
| `validation status` | Enumerated: `passed`, `flagged` (Part 7 QA raised a concern requiring review), `failed`. |
| `schema version` | Version of this metadata schema itself (Part 10), independent of `annotation_version`, since the *shape* of the metadata record can evolve separately from the *content* of any given annotation. |

**Inputs:** Outputs of every Part 3 stage plus the host execution environment.
**Outputs:** One schema-validated `annotation_metadata.yaml` per `dataset_id`.
**Dependencies:** A schema validator, consistent with Phase 14.2 Part 6's approach.
**Runtime/Memory Expectations:** Negligible — metadata population is a bookkeeping step, not a computational one.
**Failure Conditions:** Missing required field blocks the sample from being marked `annotation status: complete`; a `checksum` mismatch on later re-verification is treated identically to Phase 14.2's checksum-mismatch handling — a blocking integrity concern, not a warning.
**Validation:** Full-record schema validation as a CI gate, mirroring Phase 14.2 Part 6.
**Industrial Notes:** This schema is the annotation-layer analog of a test-and-measurement report header in a hardware characterization lab — every field exists because some future audit, reproduction attempt, or regression investigation will need it.
**Reviewer Expectations:** A populated metadata table of this completeness is what allows an AE reviewer to distinguish "this dataset's labels are reproducible" from "this dataset's labels happen to look reasonable."
**Future Extensibility:** New fields (e.g., a future `thermal_solver_version` once thermal analysis uses a dedicated external tool rather than an OpenROAD-integrated proxy) are added with a `schema version` bump, following the same backward-compatible-optional-field policy as Phase 14.2 Part 6.

## PART 6 — Annotation Storage Format

**Purpose:** Define exactly how every label and its metadata is persisted to disk, ensuring consistency, efficient access, and long-term archival integrity.

**Directory Hierarchy:**

```
labels/
└── <dataset_id>/
    ├── raster/
    │   ├── congestion.h5
    │   ├── power.h5
    │   ├── thermal.h5
    │   ├── cell_density.h5
    │   ├── macro_density.h5
    │   ├── routing_density.h5
    │   └── routing_overflow.h5      (multi-layer stack)
    ├── tabular/
    │   ├── timing.csv
    │   ├── clock_skew.csv
    │   ├── clock_latency.csv
    │   ├── wirelength_per_net.csv
    │   ├── fanout_statistics.csv
    │   └── via_density.csv
    ├── scalar/
    │   └── design_summary.yaml       (area, WNS, TNS, critical path delay, utilization, logic depth summary)
    ├── heatmaps/
    │   └── *.png                     (human-inspectable renderings of the raster labels, for QA and paper figures)
    └── metadata/
        └── annotation_metadata.yaml  (Part 5 schema instance)
```

**Format Selection Rationale:**
- **HDF5** for all raster (spatial-grid) labels — chunked, compressed, N-D array support, consistent with Phase 14.1 Part 6's rationale for the same format.
- **CSV** for all per-net/per-endpoint/per-instance tabular labels — human-readable, directly loadable by common tooling, appropriate given these are typically thousands rather than millions of rows even for the largest corpus designs.
- **YAML** for scalar per-design summaries and all metadata — human-readable, git-diff-friendly for tracking annotation-methodology changes over time.
- **PNG heatmaps** generated as a QA/publication convenience layer, not a primary data format — always regenerable from the HDF5 rasters and never treated as a source of truth.
- **Parquet/NPZ** are reserved as an optional future storage upgrade path (Part 10 forward-compatibility) for cases where per-net tabular data grows large enough (very large future OOD designs) that CSV's read performance becomes limiting; not required for the current corpus scale.

**Naming Convention:** `<dataset_id>/<category>/<label_name>.<ext>`, fully deterministic and directly derivable from the `dataset_id` alone, consistent with Phase 14.2 Part 4's addressing philosophy.

**Compression Policy:** HDF5 rasters use lossless gzip compression at a moderate level (favoring read-speed over maximum compression ratio, since these files are read far more often than written); CSV/YAML files are stored uncompressed for direct human/tool readability, with the overall `labels/` tree optionally archived as a compressed tarball for distribution (Part 14).

**Checksums:** A SHA-256 checksum is computed over the entire per-`dataset_id` label bundle (not per-file) and recorded in `annotation_metadata.yaml`'s `checksum` field, so a single checksum verifies the completeness and integrity of the whole sample in one operation.

**Inputs:** Finalized label values from Part 4.
**Outputs:** The directory tree above, per `dataset_id`.
**Dependencies:** HDF5 library, standard CSV/YAML libraries, a PNG rendering utility for heatmap generation.
**Runtime Expectations:** Heatmap rendering is the dominant cost in this stage, on the order of seconds per raster label per sample.
**Memory Expectations:** Modest; bounded by the largest single raster's in-memory representation before HDF5 writing (a few hundred MB even for the largest corpus designs at GCell resolution).
**Failure Conditions:** Write failure partway through a sample's bundle (disk-full, interrupted job) leaves an incomplete bundle, which must be detected by the checksum/completeness check (Part 7) and never mistaken for a valid sample.
**Validation:** Directory-structure completeness check (every expected file present per applicable label) plus checksum verification.
**Industrial Notes:** Separating primary data (HDF5/CSV/YAML) from convenience renderings (PNG heatmaps) mirrors standard measurement-data practice where raw data and its plotted visualization are never treated as interchangeable.
**Reviewer Expectations:** Heatmap PNGs included in the artifact bundle give AE reviewers a fast visual sanity-check path without requiring them to write their own HDF5-reading code, which measurably lowers the friction of a successful AE review.
**Future Extensibility:** The Parquet/NPZ reservation above means a future scale-up does not require a storage-format migration decision to be made under time pressure — the decision criteria are already documented.

## PART 7 — Quality Assurance

**Purpose:** Catch invalid, corrupted, or inconsistent labels before they are admitted into the finalized manifest, mirroring Phase 14.2 Part 10's QA-gate philosophy applied to labels rather than source RTL.

**Missing Labels:** Every `dataset_id` marked `annotation status: complete` must have every applicable Part 2 label present (with "applicable" determined by design characteristics — e.g., clock-metric labels are legitimately absent for clock-free combinational benchmarks and are marked not-applicable rather than missing).

**NaN Detection:** Elementwise scan of every raster (HDF5) and tabular (CSV) numeric field; any NaN triggers quarantine, consistent with Phase 14.1 Part 7's identical check applied one document earlier in the pipeline.

**Invalid Coordinates:** Bounds check confirming every spatially-indexed label (raster origin/extent, per-net endpoint coordinates) falls within the recorded die/core boundary (Part 4's Area ground truth) for that specific sample.

**Duplicate Labels:** Detection of accidental double-write (e.g., a re-run annotation job overlapping with a prior incomplete run) via `dataset_id` uniqueness enforcement at the manifest level.

**Coordinate Mismatch:** Cross-check that the coordinate system and grid origin used by every raster label (congestion, power, thermal, cell density, macro density, routing density) for a given `dataset_id` are identical — a congestion raster and a power raster for the same sample that disagree on grid origin would silently corrupt any downstream spatial correlation analysis.

**Grid Mismatch:** Cross-check that every raster label for a given `dataset_id` shares the identical grid resolution (GCell size in μm), per Part 4's stated cross-label-alignment requirement.

**Heatmap Corruption:** Basic image-file integrity check (valid PNG header, non-zero file size, dimension match against the source raster) for every generated heatmap.

**Power Sanity Checks:** Sum of per-cell power (tabular label) must match the design-aggregate power (scalar summary) within a documented tolerance (e.g., ±2%, consistent with Phase 14.1 Part 7's original power-mismatch tolerance); systematic deviation beyond tolerance flags the sample for review rather than silent acceptance.

**Timing Sanity Checks:** WNS must equal the minimum value found in the per-endpoint timing CSV; TNS must equal the sum of negative values in that same CSV — an automated cross-check that the derived-label aggregation (Part 1) was computed correctly, not just plausibly.

**Congestion Sanity Checks:** Aggregate congestion statistics (mean overflow, percentage of overflowing GCells) must be internally consistent between the per-layer routing-overflow raster (2.7) and the aggregate congestion raster (2.1), since the latter is defined as a function of the former.

**Cross-Tool Consistency:** Where two labels are derived from logically related but distinct tool outputs (e.g., placement-stage HPWL versus routed wirelength; global-route congestion versus global-route routing-density, both from the same router run), a documented consistency check verifies the expected directional relationship holds (e.g., routed wirelength ≥ HPWL for every net, with any violation flagged as an anomaly requiring investigation rather than assumed to be acceptable noise).

**Statistical Anomaly Detection:** Per-label distributional outlier detection (e.g., a design whose WNS is many standard deviations outside the corpus-wide distribution for its scale tier) flags the sample for manual review — not automatic exclusion, since legitimate extreme samples (a deliberately over-constrained design) are valuable, but silent extreme outliers are more often annotation bugs than genuine signal.

**Acceptance Criteria:** A `dataset_id` is promoted to `validation status: passed` only when all applicable checks above pass; `flagged` samples remain in the corpus but are excluded from default training/evaluation splits until manually reviewed and either cleared or excluded, consistent with Phase 14.1 Part 7's quarantine-not-drop philosophy.

**Inputs:** Finalized label bundles from Part 6.
**Outputs:** Per-`dataset_id` `qa_report.yaml`, structurally parallel to Phase 14.2 Part 10's `qa_report.yaml`.
**Dependencies:** `validate_labels.py` (Part 11).
**Runtime Expectations:** Seconds to low tens of seconds per sample, dominated by the raster elementwise scans for the largest designs.
**Memory Expectations:** Bounded by the largest single raster's in-memory footprint, consistent with Part 6.
**Failure Conditions:** Any hard-failure check (NaN, missing required label, checksum mismatch) blocks promotion; soft-failure checks (statistical anomaly) flag without blocking.
**Validation:** The QA gate itself is validated by periodic injection testing — deliberately corrupted synthetic samples run through `validate_labels.py` to confirm each check actually fires as intended, a standard test-the-tests practice.
**Industrial Notes:** This QA layer is the annotation-stage equivalent of an automated test-and-measurement pass/fail gate in a characterization lab, applied to computed rather than physically measured data but with equivalent rigor.
**Reviewer Expectations:** A per-sample QA report, aggregable into corpus-wide QA statistics (Part 9), is precisely the evidence AE reviewers look for to trust a "clean dataset" claim rather than take it on faith.
**Future Extensibility:** New checks (e.g., a future IR-drop sanity check once that label is promoted from future-work status) are added to `validate_labels.py` without restructuring the QA report schema, following the same additive-field policy established elsewhere in this document.

## PART 8 — Validation

**Purpose:** Establish the independent, higher-level validation layer confirming that the annotation pipeline as a whole — not just individual samples — behaves reproducibly across reruns, machines, and tool versions.

**Deterministic Rerun:** A designated subset of samples (spanning each scale tier: ISCAS, mid-tier, CVA6/OpenTitan) is re-annotated from identical pinned inputs (same RTL version, same tool versions, same seeds) on a periodic basis; resulting labels are diffed against the original and must match within the tolerances specified per-metric in Part 4.

**Repeatability:** Distinct from determinism — repeatability additionally varies the random seed within its documented valid range (where a stage is legitimately stochastic, e.g., certain placement-adjacent solver internals) and confirms that resulting label *distributions* (not exact values) remain stable, which is the correct standard for stages where bit-exact determinism is not achievable or not claimed.

**Cross-Machine Validation:** The same deterministic-rerun subset is additionally re-annotated on a second, independent host machine (different CPU architecture/core-count where feasible) to catch any accidental machine-specific nondeterminism (e.g., floating-point behavior differences, threading-related solver nondeterminism) not visible from same-machine reruns alone.

**Cross-Platform Validation:** Where feasible, the same subset is validated across OS/container variants (e.g., the project's reference Docker image versus a bare-metal Ubuntu install) to catch environment-dependent tool behavior differences before they become an AE-reproduction obstacle.

**Tool Version Verification:** Every validation run confirms the actually-installed tool versions match the `annotation_metadata.yaml`-recorded versions exactly before proceeding — a version drift is treated as a validation-blocking condition, not a warning, since Part 5's entire reproducibility claim depends on this match.

**Hash Verification:** The Part 6 per-sample checksum is independently recomputed and compared during every validation pass, consistent with the same discipline applied to benchmark RTL in Phase 14.2.

**Tolerance Verification:** Automated comparison of rerun results against the per-metric tolerances fixed in Part 4, with any tolerance violation treated as a validation failure requiring root-cause investigation (tool version drift, solver nondeterminism beyond expected bounds, or a genuine annotation-pipeline bug) before the affected annotation version can be considered validated.

**Regression Testing:** Every change to the annotation pipeline (tool upgrade, derivation-formula change, PDK addition) is validated against the deterministic-rerun subset before being promoted to a new `annotation_version`, preventing silent quality regressions across methodology changes.

**Golden Reference Comparison:** Where an independent, higher-fidelity reference is available for any subset of labels (e.g., a small number of samples additionally taken through a full signoff-grade STA/extraction flow purely for validation purposes, not for the main corpus), that reference serves as the accuracy ceiling against which the Part 4 accuracy claims are periodically re-benchmarked, rather than those claims being fixed once and never re-checked.

**Inputs:** The deterministic-rerun sample subset, historical annotation results, tool version records.
**Outputs:** A `validation_report.yaml` per validation pass, aggregated over time into a validation-history log.
**Dependencies:** The full Part 3 pipeline plus a second host machine/environment for cross-machine/cross-platform checks.
**Runtime Expectations:** Bounded by the size of the chosen validation subset — a representative subset (not the full corpus) is re-annotated per validation pass, keeping this tractable as a periodic (not per-commit) process.
**Memory Expectations:** Consistent with Part 3's per-sample figures for whichever samples are included in the validation subset.
**Failure Conditions:** Any of the checks above failing halts promotion of the associated annotation-pipeline change or `annotation_version` bump until resolved.
**Validation:** This part is, itself, the validation layer — its own correctness is established by periodic manual audit of a small number of validation reports rather than further automation, an acceptable and standard terminal point for a QA hierarchy.
**Industrial Notes:** This mirrors a production test-and-measurement lab's periodic gauge-repeatability-and-reproducibility (Gauge R&R) study, applied to a computational rather than physical measurement process.
**Reviewer Expectations:** A documented validation history (not just a one-time claim) is a strong, differentiating signal of dataset rigor for TCAD/TVLSI-caliber reviewers specifically, who tend to have production EDA-tool backgrounds and recognize this practice.
**Future Extensibility:** The golden-reference-comparison mechanism generalizes directly to any future label category requiring an accuracy-ceiling benchmark, without process changes.

## PART 9 — Dataset Statistics

**Purpose:** Automatically generate corpus-wide statistical reports characterizing the annotated label set, supporting both internal QA and direct inclusion in publication supplementary material.

**Automatically Generated Content:**
- **Distribution plots** — histogram and kernel-density visualization for every scalar and raster-aggregate label (WNS, TNS, utilization, congestion mean, power mean, etc.), generated per split-role hint (train/zero-shot/OOD, inherited as metadata from Phase 14.2) so distributional shift across splits is visible at a glance.
- **Mean, median, variance** — computed per label, per split, per PDK, and per benchmark scale-tier, to support the kind of stratified reporting TCAD/ICCAD reviewers expect rather than a single corpus-wide number that obscures scale-dependent behavior.
- **Histogram** — as above; additionally generated per-layer for the multi-layer routing-overflow label (2.7), since layer-aggregated statistics alone would obscure known layer-dependent congestion concentration.
- **Correlation** — pairwise correlation matrix across the full label set (e.g., congestion vs. cell density, power vs. thermal, macro density vs. congestion), both as a sanity-check tool (Part 7's cross-tool consistency logic operates at the individual-sample level; this operates at the corpus level to catch subtler systemic issues) and as directly citable evidence for a paper's motivation section.
- **Class imbalance** — for any label that is used in a binarized/thresholded form downstream (e.g., "overflowing" vs. "non-overflowing" GCells), the corpus-wide class balance is reported explicitly, since this is directly relevant to any future (out-of-scope-here) model-evaluation methodology and its omission is a common reviewer objection.
- **Outlier detection** — corpus-wide flagging of samples whose label values are statistical outliers relative to their scale-tier peer group, cross-referenced against Part 7's per-sample anomaly flags to distinguish "flagged for QA reasons" from "genuinely extreme but valid."
- **Coverage** — a completeness matrix (benchmark × PDK × utilization-variant × label-category) showing exactly which combinations have been annotated, directly supporting Part 3's stage-availability tracking and making any coverage gaps visible rather than discovered late.
- **Technology statistics** — label distributions stratified by PDK/technology-node, supporting the cross-PDK/cross-node generalization claims established in Phase 14.1's split strategy.
- **Benchmark statistics** — label distributions stratified by originating benchmark suite (ISCAS vs. OpenCores vs. RISC-V-core-family, etc.), supporting per-suite quality auditing.

**Inputs:** The finalized, QA-passed label corpus (Part 7 output) plus Phase 14.2's benchmark/split metadata.
**Outputs:** `stats/dataset_statistics.csv`, `stats/feature_histograms.json` (label-focused, not to be confused with Phase 14.1's feature-focused file of a similar name — namespaced separately as `stats/label_statistics.json` to avoid ambiguity), publication-ready LaTeX tables, and rendered plots.
**Dependencies:** Standard statistical/plotting libraries; no EDA tool dependency at this stage, since it operates purely on already-generated label data.
**Runtime Expectations:** Minutes for the full corpus, dominated by correlation-matrix computation across the full label set at corpus scale.
**Memory Expectations:** Modest; bounded by loading the full tabular/scalar label set into memory simultaneously (raster labels are summarized via streaming aggregate statistics rather than fully loaded, to keep this tractable at corpus scale).
**Failure Conditions:** A stratification cell (e.g., a specific benchmark × PDK combination) with zero samples is reported explicitly as a coverage gap rather than silently omitted from the output tables.
**Validation:** Cross-check that every reported statistic's underlying sample count matches the coverage matrix, catching silent double-counting or omission bugs in the statistics-generation code itself.
**Industrial Notes:** This report is the annotation-layer counterpart to a wafer-lot summary report in fab characterization — a standard, expected deliverable rather than an optional nicety.
**Reviewer Expectations:** Stratified (not just aggregate) statistics, plus an explicit coverage matrix, are what separates a dataset paper's statistics section from a superficial "here is a histogram" figure.
**Future Extensibility:** New label categories (IR drop, EM) automatically participate in this statistics generation once promoted from future-work status, since the statistics pipeline operates generically over whatever labels are present in the corpus rather than hardcoding the current twenty-category taxonomy.

## PART 10 — Version Control

**Purpose:** Define independent, precisely-scoped versioning for every layer of the annotation subsystem, preventing the ambiguity that arises when "dataset version" is used loosely to mean several different things at once.

**Dataset Version:** Inherited from Phase 14.1 (the RTL-to-GDSII sample generation version) — this document does not redefine it, only consumes it as an input identifier (`version` field, Part 5).

**Annotation Version:** Defined and owned by this document (Part 1, Part 5) — semantic versioning where MAJOR bumps correspond to a labeling-methodology change (new derivation formula, new tool for an existing label category), MINOR bumps correspond to tool-version upgrades that do not change methodology, and PATCH bumps correspond to bugfix re-annotation with no methodology or tool-version change.

**Schema Version:** Defined and owned by this document for the `annotation_metadata.yaml` schema (Part 5) specifically — versioned independently of `annotation_version` since the *shape* of the metadata record and the *content/methodology* of the labels evolve on independent timelines, exactly as Phase 14.2 Part 6 established for benchmark metadata.

**Manifest Version:** A further-independent version for the aggregate `labels/manifest.yaml` structure (Part 11/12) itself, following the same reasoning — the manifest's own structure (which fields it aggregates, how it cross-references Phase 14.2's manifest) can change without any individual sample's annotation or schema version changing.

**Backward Compatibility:** A `schema version` or `manifest version` bump is required to remain backward-compatible (old, lower-schema-version records remain readable by tooling built against the new schema, via optional-field handling) unless explicitly marked a breaking MAJOR schema revision, which is reserved for rare, clearly-justified cases and always accompanied by a migration note.

**Forward Compatibility:** Tooling built against a given schema version is expected to gracefully ignore unknown fields introduced by a later MINOR schema bump, rather than failing outright — a standard robustness principle applied consistently with Phase 14.2's equivalent policy.

**Inputs:** Every versioned artifact produced elsewhere in this document.
**Outputs:** A version-registry entry per artifact type, aggregated in the top-level manifest (Part 12).
**Dependencies:** None beyond the schema validator already established in Part 5.
**Runtime/Memory Expectations:** Negligible.
**Failure Conditions:** Any artifact referencing an undeclared or inconsistent version combination (e.g., an `annotation_version` bump not accompanied by an updated methodology-change log entry) is treated as a manifest-validation failure.
**Validation:** Manifest-level consistency check confirming every version field is populated and internally consistent (e.g., no `dataset_id` referencing an `annotation_version` that does not exist in the version-history log).
**Industrial Notes:** Four independently-scoped version axes (dataset, annotation, schema, manifest) is deliberately more granular than most academic dataset papers bother with — this granularity is what allows precise, unambiguous bug reports and corrections years after initial publication.
**Reviewer Expectations:** This level of versioning discipline is above the norm and is intended, consistent with Phase 14.2's closing note, to preempt rather than merely survive AE scrutiny.
**Future Extensibility:** The four-axis versioning scheme accommodates any future artifact category (e.g., a hypothetical future "solver-configuration version" if thermal/IR-drop solvers gain their own independent tunable-configuration versioning) by adding a fifth axis without disturbing the existing four.

## PART 11 — Automation

**Purpose:** Specify the tooling operationalizing Parts 3–10, at the level of responsibility and interface, consistent with Phase 14.2 Part 11's approach.

| Script | Responsibility |
|---|---|
| `generate_labels.py` | Executes Part 3's full label-generation pipeline per `(benchmark_id, floorplan_variant)` sample: runs Synthesis through Label-Generation stages, applies Part 4's ground-truth extraction logic, and populates the initial label bundle (Part 6 directory structure). Supports resume via per-stage checkpoint hashing, consistent with Phase 14.1's resume philosophy, and supports `--cluster slurm`/`--cluster k8s` execution. |
| `validate_labels.py` | Runs Part 7's full QA check suite per sample, emits `qa_report.yaml`, and exits non-zero on any hard-failure check so it can serve as a CI gate; also implements the periodic injection-testing self-check described in Part 7. |
| `statistics.py` | Generates Part 9's corpus-wide statistical reports, plots, and publication-ready tables. |
| `annotation_manifest.py` | Aggregates every sample's `annotation_metadata.yaml` and `qa_report.yaml` into the top-level `labels/manifest.yaml`, applying Part 5's schema validation and refusing to include any sample lacking `validation status: passed` (or explicitly, documented `flagged` status with reviewer sign-off). |
| `heatmap_generator.py` | Renders Part 6's PNG heatmap convenience layer from the primary HDF5 raster labels; strictly a derived-output generator, never a source of label data. |
| `checksum_generator.py` | Computes the per-sample bundle checksum (Part 6) and the corpus-wide checksum ledger, consistent with Phase 14.2's checksum discipline. |
| `metadata_validator.py` | Standalone schema-validation utility for `annotation_metadata.yaml` records, usable independently of a full annotation run (e.g., for validating a manually-corrected metadata record after a flagged-sample review). |

**Inputs (all scripts):** The Phase 14.2 benchmark manifest, the Phase 14.1 sample/floorplan-variant configuration, and (for validation-focused scripts) prior annotation outputs.
**Outputs (all scripts):** Populated `labels/` tree, QA reports, statistics artifacts, and the aggregate manifest, all machine-validated.
**Dependencies:** The full Part 3 tool chain (Yosys, OpenROAD, OpenSTA), HDF5/CSV/YAML libraries, a schema validator, a plotting library, standard checksum utilities.
**Failure Modes:** `generate_labels.py` failures are isolated per-sample (consistent with Phase 14.2's per-benchmark isolation philosophy) and logged with structured error records rather than halting the full corpus run; `validate_labels.py` and `annotation_manifest.py` failures block only the affected sample's promotion to `validation status: passed`, never silently downgrading a failing sample to passing status; `statistics.py` failures (e.g., a coverage gap) are reported as warnings in the generated report itself rather than halting statistics generation for the rest of the corpus.
**Runtime/Memory Expectations:** Consistent with the per-stage figures already established in Parts 3, 6, 7, and 9 of this document, since these scripts are the direct operational implementation of those specifications.
**Cluster Execution:** All scripts follow the identical per-sample, manifest-driven, Slurm-array/Kubernetes-indexed-job parallelization pattern established in Phase 14.1 Part 9 and Phase 14.2 Part 11, ensuring a single consistent cluster-execution model across all three phases of the project to date.

**Industrial Notes:** Seven narrowly-scoped scripts, each independently testable and independently re-runnable, mirrors the same CI/CD decomposition philosophy applied in Phase 14.2 Part 11 — e.g., a methodology fix affecting only the timing-derivation formula requires re-running only `generate_labels.py`'s label-generation stage and `annotation_manifest.py`, not the entire pipeline.

**Reviewer Expectations:** Providing these seven scripts as artifact-bundle components, precisely scoped as specified here, is what earns the AE "Functional" and "Reproducible" badges at the annotation layer, exactly as Phase 14.2's four scripts did at the acquisition layer.

**Future Extensibility:** New scripts (e.g., a future `golden_reference_compare.py` operationalizing Part 8's golden-reference-comparison mechanism as a standalone, on-demand tool) slot into the same per-sample, manifest-driven pattern without disrupting the existing seven.

## PART 14 — Publication Readiness

**IEEE TCAD / TVLSI / DAC / ICCAD / DATE Fit:** This document's per-label definition/tool-origin/units/resolution/tolerance/accuracy structure (Part 4) directly answers the standard ground-truth-provenance questions reviewers at these venues raise, and its explicit stage-to-label availability mapping (Part 3) supports an honest, defensible framing of any early-stage-input-to-late-stage-label predictive claim made in a downstream modeling paper.

**Artifact Evaluation:** The combination of pinned tool versions, deterministic-rerun validation (Part 8), and the seven automation scripts (Part 11) satisfies AE's "Functional" and "Reproducible" criteria at the annotation layer, extending the same guarantees Phase 14.2 established at the acquisition layer one stage further downstream.

**Zenodo / DOI:** The finalized `labels/` tree, alongside its manifest and version-history registry, is a natural companion Zenodo deposit to the Phase 14.2 benchmark-corpus deposit, ideally cross-referenced by DOI in both directions (the label deposit's metadata citing the exact benchmark-corpus DOI/version it was annotated against, and vice versa) so the full provenance chain from RTL acquisition through ground truth remains resolvable as a single citable unit.

**Reproducibility:** The `annotation_metadata.yaml` schema (Part 5) plus the deterministic-rerun/cross-machine validation discipline (Part 8) together constitute the specific, checkable reproducibility claim this document makes — not a general assurance, but a stated, testable one.

**Long-Term Archival:** Consistent with Phase 14.2 Part 14's reasoning, upstream EDA tool releases are not guaranteed to remain indefinitely available in their exact pinned form; the recorded tool-version metadata (Part 5) is retained even where the tool binary itself cannot be re-archived, so that at minimum the *claim* of what was used remains permanently auditable even if bit-exact tool reproduction becomes infeasible decades later.

**Industrial Deployment:** The annotation subsystem's structure — independently versioned labels, immutable-once-published records, a QA gate mirroring production characterization-lab discipline — is directly transferable to an industrial EDA-ML pipeline, not merely an academic-reproducibility convenience; this dual academic/industrial applicability is itself worth stating explicitly in a paper's broader-impact or industrial-relevance discussion.

**Reviewer Expectations:** Taken together with Phase 14.2, this document is intended to preempt the two most common ML-for-EDA dataset-paper objections in sequence — "is your source RTL corpus properly licensed and versioned" (Phase 14.2) and "is your ground truth properly defined, tool-traceable, and reproducible" (this document) — leaving Phase 14.4's feature-extraction specification to address the remaining, distinct objection class around feature engineering and representation choices.

**Future Scalability:** Nothing in this specification is tied to the current twenty-category label taxonomy — the annotation philosophy, pipeline structure, ground-truth-specification format, metadata schema, storage design, QA gate, validation methodology, statistics generation, versioning scheme, and automation interface all generalize directly to future label categories (starting with IR drop and EM, already schema-reserved in Part 2) without structural revision to this document.
